# 파워리프팅 트래커 (단일 HTML) — 진행 내역

> 대상 파일: `파워리프팅-트래커-32.html` (React+Babel CDN, 단일파일, 메인 엔진 앱과 별개)
> 배포: https://aa26178787.github.io/powerlifting/tracker.html (public/tracker.html, 메인 앱과 같은 Pages에 정적 서빙)
> DB: Firebase Firestore (`powerlifting/main` 문서, 기기 간 실시간 동기화)
> 최종 갱신: 2026-07-29

## 배경
기존엔 `window.storage`(존재하지 않는 API)를 써서 새로고침/재접속 시 데이터가 날아가는 상태였음. 이번 세션에서 영속화·기기 간 동기화·과거 기록 수정·TM 자동조절 로직까지 순차 추가.

## 주요 변경

1. **데이터 영속화**: `window.storage` → `localStorage` 교체 (새로고침/재접속 유지)
2. **과거 날짜 수정 가능**: 오늘 탭에서 과거 날짜 선택 시 읽기전용 카드 → 오늘과 동일한 인라인 입력(`TodayCard`)으로 교체, `date`/`cycle`/`week` prop을 일반화해 임의 날짜 기준 저장·매칭
3. **기록 탭 날짜 입력 버그 수정**: 수동 입력이 항상 오늘 날짜로만 저장되던 문제 → 이후 아예 수동 세트입력 폼 제거(오늘 탭 인라인 입력으로 통합)
4. **세트 위치 밀림 버그 수정**: 로그를 배열 위치(idx)로만 매칭해 중간 세트 삭제 시 백오프 기록이 앞으로 밀리던 문제 → 저장 시 `setIdx` 고정 태그 부여, 그 값으로 매칭
5. **3주차 싱글 실시간 연동**: 오늘 탭에서 "기입" 싱글 세트 저장 시 사이클 탭의 싱글 실측 필드(`S.singles`)에 자동 반영 → 92%/86.5% 백오프 무게 즉시 재계산 (단, 조작 대상이 현재 진행 사이클일 때만 반영해 과거 사이클 오염 방지)
6. **기기 간 동기화**: Firebase Firestore 연결 (`localStorage`는 오프라인 캐시로 유지), Firestore 규칙은 `powerlifting/main` 문서만 개방
7. **GitHub Pages 배포**: `public/tracker.html`로 정적 배포, push 시 기존 `deploy.yml`이 자동 빌드/배포 — **이후 수정은 항상 `public/tracker.html` 동기화 + commit + push까지 자동 진행**(사용자 지시)
8. **오늘 탭 UX**: 사이클 28일(1~4주차) 전체를 날짜 스트립에 노출(과거 수정 + 미래 루틴 미리보기), 주차별 카드형 컨테이너로 시각 분리, 오늘 위치 자동 스크롤
9. **날짜별 기록 내보내기**: 설정 탭의 "전체 기록 내보내기"(최근 30개, AI 채팅 붙여넣기용) 제거 → 오늘 탭 상단에 "그 날짜 기록만" 내보내는 버튼으로 교체, 무게 없는 보조운동은 방어적으로 필터링
10. **기록 탭**: 날짜 최신순 정렬 + 날짜별 섹션 헤더
11. **중딥 백오프 세트 수 수정**: 4세트 → 3세트, "탑1+백3" 라벨 → "탑1+백2"
12. **TM(트레이닝 맥스) 사이클 전환 로직** (스쿼트·벤치·데드 전용, 중딥/중량풀업은 기존 방식 유지):
    - **신호1 (완전 자동)**: AMRAP 세트(1/2주차 3세트째, 3주차 86.5%) 초과렙 → 인상폭 배율(0/0.5/1/2×) 자동 계산, 사이클마다 누적 적용
    - **신호2 (승인 필요)**: 3주차 고정렙 세트(기입싱글·92%) RPE 여유 → "TM 재산정 권장" 배지만 표시, 자동 반영 없음
    - **재산정 승인 플로우**: confirm 다이얼로그 → 승인 시 TM 숫자를 직접 덮어쓰지 않고 트리거 세트의 무게/렙/RPE를 TM 입력 필드에 대입 → e1RM·적용TM 기존 공식으로 재계산 → 재기준(baseCycle) 이후 신호1 인상폭이 그 위에 얹힘 (재산정 → 인상폭 순서 보장)

### 사고 기록 — 라이브 Firestore 오염
디로딩 스킵 버튼을 브라우저 자동화로 검증하던 중, 날짜를 mock한 세션에서 실제 버튼을 클릭해 `save()`가 그대로 프로덕션 Firestore(`powerlifting/main`)에 반영됨 — 실제 `startDate`가 `2026-07-08` → `2026-07-02`로 오염. 즉시 발견해 앱의 설정 탭 입력을 통해 `2026-07-08`로 복구, 새 세션(캐시 없는 fresh fetch)으로 Firestore 반영 확인 완료. **교훈**: 이 앱은 mock-데이터/스테이징 환경이 없고 클라이언트 코드가 실제 운영 DB에 직접 연결되어 있음 — 저장(`save()`)을 유발하는 버튼은 실제 기기 화면에서만 클릭하거나, 자동화 검증 시 반드시 Firestore 요청을 차단(`page.route`)하고 진행할 것.

## 2026-07-29 세션 — RPE+렙 이중 웨이브 전면 개편 (AMRAP·TM 폐지)

사용자가 4일 구조 최종 스펙을 제공 → `public/tracker.html` 전체 재작성. 핵심 변경:

1. **AMRAP·TM 폐지**: 신호1(AMRAP 초과렙 배율)·신호2(TM 재산정 승인)·`S.singles` 입력 UI 전부 제거. 3대(스쿼트·벤치·데드)는 이제 e1RM에서 직접 %를 산출(TM 90% 버퍼 없음). e1RM 갱신은 3주차 "진짜 싱글"(RPE9×1) 실측 로그를 사이클마다 자동으로 읽어 재계산 — 처방보다 여유 있었으면 자동으로 위로, 딱 맞았으면 공식상 자연히 유지(별도 승인 절차 없음). `manual` 필드로 수동 override는 유지.
2. **요일 구조 전면 교체**: 월(볼륨스쿼트·라슨벤치 변형 + 중딥4×5 + 로우 + Core) / 화(템포벤치·정지데드 변형 + 중량풀업4×5 + 사이드델트 + 바이셉스) / 수(메인 스쿼트→벤치 앵커, 5분 휴식 + Chest ISO) / 목(순수 보조: 슈러그·리스트컬·리버스리스트컬·트라이셉스·바이셉스) / 금(메인 데드 앵커 + 클로즈그립벤치 변형 + 정지딥스 + 상단하프친업 + 리어델트). 4주차(디로드)도 동일 요일 구조 유지, 웨이브 표만 가벼워짐(메인 RPE6×3, 변형 RPE5×5) — 스펙이 디로드 행을 명시했기 때문. 딥/풀업은 디로드 주엔 4×5 수행하되 증량 판정은 건너뜀.
3. **렙 상한 vs 웨이브 표 충돌**: 스펙의 웨이브 표(렙수)가 스쿼트·벤치·데드 "공통"으로 적혀 있는데 렙 상한(스쿼트8·벤치6·데드4)은 종목별로 다름 — 예: 메인 1주차 데드 5회(상한4 초과), 변형 3주차 벤치/데드 계열 8회(각 상한 초과). 사용자 확인: **상한 우선, 상한 렙수+원래 RPE로 %e1RM 재계산**(`pctOfE1rm(rep,rpe)=30/(40+rep-rpe)`, e1RM 공식의 역함수). 볼륨스쿼트는 상한과 정확히 일치해 그대로, 벤치 변형 3주차는 8→6회(75%), 정지데드는 거의 매주 캡됨(1주 3회만 그대로, 2주 83.3%/3주 78.9%/4주 76.9%로 재계산).
4. **중딥·중량풀업**: "탑1+백오프2"(TM 기반) 구조 폐지 → 4×5 스트레이트로 교체. 마지막(4번째) 세트 RPE로 다음 세션(매주) 자동 증량: ≤6.5 +5kg(딥+10lb) / 7~7.5 +2.5kg(딥+5lb) / 8 +1.25kg(딥+2.5lb) / 8.5+ 유지. 저장 스키마를 `{w,reps,rpe,manual,inc}`(e1RM 계산용) → `{weight,unit,inc}`(직접 작업무게 ratchet)로 변경 — **라이브 사용자 기존 데이터 보존을 위해 `legacyWorkingWeight()`가 `weight` 필드 없을 때 구 TM 공식으로 1회 이관**(마이그레이션 쓰기 없이 읽기 시점 폴백).
5. **Settings/Projection/CompPredict**: TM 표시 제거, e1RM 단일 값으로 통일(`E1`/`E1ALL` 맵). 예측 탭의 "인상폭"은 처방 로직과 완전히 분리된 순수 예측용 수동 입력으로 존속(딥은 lb 작업무게지만 예측 인상폭은 kg 환산으로 입력받아 목표(GOALS, kg 기준) 비교와 단위 정합).
6. **RPE 판정·그립 규칙**: 코칭 텍스트로 사이클 탭 하단에 반영(바스피드 판정표, 애매하면 높은 쪽, 8 vs 8.5 경계, 스트랩/맨손 규칙). 앱 로직에는 영향 없음(수동 자기평가 영역).
7. **검증**: Firestore/React CDN 의존이라 로컬 헤드리스 브라우저(puppeteer/playwright) 미설치 — 실행 검증은 못함. `@babel/parser`로 JSX 구문 파싱만 확인(통과). 숫자 공식은 스펙 예시 값(78.9%/85.7%/93.75%/81.1%, 88.2%/81.1%/71.4%/75%)과 손계산으로 교차검증.
8. 커밋 전 `docs/TRACKER_LOG.md` 갱신 규칙(항상 `public/tracker.html` 동기화+commit+push) 그대로 따름.

**배포 후 버그 수정**: 변형(볼륨스쿼트·라슨벤치·템포벤치·정지데드·클로즈그립벤치) 종목이 전부 "1세트"로 나가고 있었음 — 스펙 표에 세트수가 명시돼 있지 않아 구시스템("메인 각 1세트") 관행을 그대로 복사한 실수. "볼륨 스쿼트"인데 1세트인 건 이름과 모순된다는 사용자 지적으로 확인 → 변형은 **같은 %·RPE·렙으로 3세트 반복**, 메인(스쿼트·벤치·데드, 3주차 진짜 싱글로 수렴하는 탑 세트 설계)은 1세트 유지.
